# Taskloom 任务系统产品需求草案

# 产品定位与需求状态

版本：需求草案 v0.8。日期：2026 年 11 月 17 日。

Taskloom 是面向企业中人与 Buddy 协作的任务系统。本项目只建设任务系统；软件分发与管理平台、Agent 执行层均已具备，直接复用，不在本项目中重建。Buddy 是已有 Agent 层中接入任务系统的执行主体。任务是人与 Buddy 持续协作的基本单位：每个任务有一个独立 commit 时间线，过程按时间记录，目标、验收标准和最终结果单独展示。任务树表达分解和协作，状态与版本历史表达工作的当前情况和演进过程。

长期目标是 Buddy 在授权范围内自行判断可行性并执行，人主要设置目标、作关键决策和验证结果。不同 Buddy 可以专门承担规划、执行、审查或目标维护职责。自主程度由各 Buddy 的接口权限决定，不依赖另建一套自动化流程。

模块边界见[架构](architecture.md)，共用 API 见 [API 与权限](api.md)。

## 已确认的产品约束

- 本项目只建设任务系统；软件分发与管理平台、Agent 执行层复用已有能力。任务系统的重构不包含上述已有系统的重建。

- 对接运行在个人电脑和云端电脑上的已有 Buddy；安装、分发、升级及 Agent 运行时由已有系统负责。Harness 可以作为已有 Agent 层的内部执行实现，不属于本项目建设内容。

- 每个任务对应独立的协作时间线，同时保留任务状态转换和任务分解。

- 任务默认由人负责，处理人可以是人或 Agent（Buddy）；人工处理人可以自己提交结果，也可以再转交给 Agent。更换处理人或运行实例，不自动改变负责人和验收人。

- 目标、验收标准、结果应独立于消息流展示，且能够追踪历史变化。

- 支持任务树及类似 Git 的当前状态、历史变更和版本查看。

- 用户自己创建的任务，默认可由自己的 Buddy 处理；他人交给用户的任务，由 Buddy 先判断，不确定再请用户确认。

- 普通执行 Buddy 初期不默认获得拆解、转交和调整正式计划的权限；专门授权的 Buddy 可以获得这些能力。

- 不同职责的 Buddy 可拥有不同权限。人和 Buddy 使用同一套业务能力，后续主要通过开放接口权限扩大自主范围。

- 部分任务可配置验收流程，不强制所有任务采用相同验收方式。

配置采用 base.yaml + config.yaml 两层：base 承载主要能力、完整默认装配及全局默认值；日常维护者只维护 config，覆盖同实例配置。不同流程示例为 config 编辑参考，不增加运行时配置层。详见[配置说明](configuration.md)。

## 需求成熟度

M01 的身份、执行保护、验收、公共事务及分期范围分别以[核心契约](core-contracts.md)和 [README](../README.md#当前状态) 为准。业务模块及 API 尚未实现；流程步骤由任务事实推导。剩余外部协议和量化指标集中列于末章。本文不选择开源底座、具体 SQL 数据库或模型供应商；客户端通信已确定为共用 HTTP 业务 API 与 WebSocket 变化推送。

# 本项目范围与外部依赖

## 建设范围与职责划分

| 系统及范围归属 | 核心职责 | 能力边界 | 不承担的职责 |
| --- | --- | --- | --- |
| 已有软件分发与管理平台（外部依赖） | 管理 Buddy 的交付与生命周期 | 软件包分发、设备及实例注册、版本渠道、升级与回退策略、运行健康、实例启停与撤销 | 不持有任务业务状态，不决定任务是否完成或验收通过 |
| 已有 Agent 层／Buddy（外部依赖） | Agent 执行主体 | 理解任务、判断可行性、运行commit 时间线、调用工具、管理本地执行上下文、汇报进度、请求决策、提交结果；按授权承担规划或审查 | 不自行扩大权限，不绕过任务系统修改共享任务事实 |
| 任务系统（本项目建设） | 管理工作的目标、协作、状态和历史 | 任务commit 时间线、任务树、依赖、分配与交接、状态、版本、结果、验收、任务权限、执行所有权 | 不安装升级 Buddy，不承载具体模型推理和本地工具执行 |

上表用于界定本项目与已有系统的集成边界，不表示本项目需要交付三个系统。已有能力是否满足对接要求，需要在设计阶段核验；接口适配需求应明确归属，不默认扩展为重建外部系统。

## 与已有系统的对接要求

- 管理平台向任务系统提供 Buddy 身份、有效实例、版本及可用性信息。任务系统据此判断是否可分配；分配和执行状态由任务系统管理。

- 前端和 Buddy 共用 HTTP 业务 API，按权限读取详情、前后版本、消息、材料和历史，并提交进度和交付。WebSocket 推送任务变化；已有 Agent 层将变化用作 steer，自主决定读取和处理，不由任务系统组装 Agent 上下文或远端派发运行。

- Buddy 可以在 Harness 中通过 platform:task 接入。任务系统提供稳定的业务接口，不依赖某个具体 Harness 实现。

- 企业、成员及逻辑 Buddy 的身份应统一引用；身份注册归属和身份服务实现待设计。任务授权由任务系统执行，设备管理权限由管理平台执行。

- Buddy 的工具凭证和工具访问授权由执行环境及相应凭证机制管理。任务系统保存权限要求和必要引用，不把工具密钥放进任务对话。

- 管理平台记录升级和设备日志；任务系统记录业务执行与任务变更。Buddy 升级或重启不应清除任务历史。

## 产品交付边界

任务系统应能够以自身品牌和企业配置交付，解除对现有 NEX 专有业务概念的强绑定；交付时明确所依赖的已有管理平台和 Agent 层及其接口要求。个人电脑与云端 Buddy 使用一致的任务协议。任务系统采用首版按单企业部署验证，保留租户隔离；共享 SaaS 运营后置。

# 参与者与核心对象

## 参与者

| 身份 | 含义 |
| --- | --- |
| 创建者 | 发起目标或任务的人或有创建权限的 Buddy |
| 负责人 | 默认由人担任，对任务推进、关键决策和最终交付负责 |
| 执行者 | 承担任务具体工作的 Agent（Buddy），与人的负责人分别记录 |
| 协作者 | 提供信息或承担部分工作的人和 Buddy |
| 规划者 | 维护分解、依赖及正式计划的授权参与者 |
| 审查者或验收者 | 检查结果并按配置提出意见、通过或退回 |
| 授权管理者 | 在自身权限范围内授予、收回 Buddy 能力的人或管理角色 |

角色可以组合，但不能因参与commit 时间线就自动获得修改目标、转交或验收权限。任务交给用户时，用户的 Buddy 可以作为执行者代理参与，系统同时保留人的负责人、执行 Buddy 和实际操作者；具体运行实例记录在执行记录中。

## 建议的核心对象

| 对象 | 必须表达的信息 |
| --- | --- |
| 企业与工作范围 | 企业身份、成员、项目或任务集合、访问边界 |
| 逻辑 Buddy | 持续身份、归属或管理者、职责、权限配置 |
| Buddy 实例 | 个人或云端电脑上的具体运行实例、在线状态、版本；实例不等于另一个逻辑 Buddy |
| 任务 | 稳定标识、目标、输入、验收标准、角色、状态、正式计划、当前结果 |
| 任务关系 | 父子分解、阻塞依赖、替代或关联关系 |
| commit 记录 | 消息、进展、请求、决策、变更和交付事件 |
| 执行记录 | 执行主体及实例、依据版本、所有权、进度、检查点引用、结果和结束原因 |
| 版本与变更 | 修改范围、前后内容、操作者、原因、时间及关联记录 |
| 交付与验收 | 结果 CommitID及材料版本引用、交付版本、执行与目标/标准依据、验收者、结论和意见 |

建议先统一使用任务节点承载目标及其分解：根任务可表示较高层目标，子任务表示支撑工作。独立 Goal 实体首版后置，不因该选择阻塞普通任务使用。

建议任务允许脱离项目独立存在；项目用于组织与授权，不成为创建任务的必要步骤。

# 任务commit 时间线与核心能力

## 创建和任务信息

任务支持标题、目标说明、背景与输入材料、验收标准、优先级、期限、参与者、负责人和可选验收流程。人、获授权的 Buddy 及外部系统均可创建。

用户可以先输入自然语言，Buddy 帮助澄清并整理结构化字段；缺少信息时允许保留待补充项，不得把推测默认为已确认要求。可执行性判断应覆盖信息、能力、权限和环境，不能确定时提出具体问题或处理建议。

## 协作时间线

- 一任务一条 commit 时间线，消息和过程按服务端可确定的顺序持续记录，同时保留客户端发生时间。

- 支持文本、附件、链接、回复引用、提及参与者、未读及通知。

- 人与 Buddy 都可发言；展示身份及消息类型，避免系统事件与 Buddy 判断混淆。

- 消息类型至少区分普通交流、进度、请求输入或决策、正式决策、状态与版本事件、结果提交、验收意见。

- 任务详情单独展示当前目标、验收标准、状态、负责人、子任务概况和当前交付结果，能跳转到对应历史。

- 对话中的建议不自动成为正式变更。修改目标、拆解、转交、验收等必须形成经过权限校验的业务操作。

- Buddy 不因每条消息都必须启动执行；应区分讨论、明确分配、正式变更和需要处理的事件，避免相互回复无限循环。

## 请求输入和决策

请求必须说明问题、需要谁回答、为何阻塞、可选方案和建议。答复应关联原请求；请求具有待处理、已处理或已失效的可追踪状态。自然语言答复若存在歧义，应澄清后再改变关键业务状态。

任务等待时展示在等谁、等什么。通知与提醒不替代请求本身的持久记录。

## 交付和验收

默认交付物是 Agent 明确提交的结果回复，可包含文本、文件版本引用和链接。回复正文仅保存在任务commit 时间线中，交付登记固定结果 commit、执行及目标/标准依据，结果区展示同一份内容。普通交流、进度和提问不自动交付。默认不强制额外完成表单或逐项标准回应；特殊任务通过新增状态步骤表达质量或事实审核。更正追加新 commit 引用旧记录，不改写已有交付与验收依据；新结果通过再次提交登记。详见[结果回复交付](core-contracts.md#交付与验收)。

任务创建时固定验收方式 manual/none，验收人为负责人。验收结论绑定具体交付，换交付后旧结论不再适用。无需独立验收也须满足当前轮结果、依据和依赖条件；多级/会签后置。

## 查询与外部接入

人和 Buddy 均能按权限查询任务、commit 时间线、任务树、状态、历史版本、差异、执行、交付及验收。提供搜索、过滤、分页及历史增量获取，不要求 Buddy 每次加载完整历史。

业务接口支持外部系统创建和查询任务、关联外部业务标识、接收任务事件。任务生命周期及权限语义应独立于 UI、MCP 或具体执行框架。

# 任务树与依赖

## 分解模型

一个任务可以拆成多个子任务，子任务可继续分解。每个节点保留独立 commit 时间线、目标、验收标准、负责人、状态、版本、执行与结果。不同节点可以分配给不同 Buddy 并行处理。

首版每任务最多一个父任务；共享产物通过关联与依赖表达。默认不开放跨项目/跨树依赖，单企业和任务范围规则见覆盖表。

## 树的操作

授权主体应能创建子任务、修改分解、调整父子关系与顺序、分配和转交、维护依赖、取消或替换节点。拆解、转交、计划调整是独立权限，普通执行权限不隐含这些能力。

- 批量拆解应能作为一个完整变更查看，避免只看到零散节点而不理解计划。

- 任务移动后保持稳定标识和原commit 时间线历史，记录原位置、新位置和原因。

- 移动不能隐式绕过权限；如影响访问范围，需单独校验和明确提示。

- 取消、替代和移出当前计划保留历史关系；历史查看应能还原当时的树。

- 禁止父子环及阻塞依赖环。树关系修改与依赖修改均需检查一致性。

## 依赖与进展

父子关系表示工作分解，依赖表示执行前置条件。前置条件未满足时，任务展示阻塞原因；解除后通知相应执行者。

父任务展示子任务完成情况、失败执行、等待项、待决策项和待验收项。进度统计需说明口径，不把子任务数量比例等同于目标完成度。

子任务完成不自动证明父目标达成；父任务须有自己的结果和完成检查。父取消不默认级联；整树操作必须显式选范围授权。已完成任务不可重开，已完成父任务不再调整正式子计划，返工新建任务；子取消不满足完成依赖。

## 上下文与权限

子任务可引用父目标、相关决策和上游产物。引用不自动授予原始材料的读取权。执行 Buddy 应能看到授权范围内完成工作所需的全部状态，包括相关历史；无权限部分不得通过父任务摘要或结果引用泄露。

## 示例

“完成客户行业研究”为根任务，下设资料收集、竞品分析和报告撰写。两个 Buddy 分别处理前两项；报告撰写依赖两项交付。根目标改为“只关注国内市场”后，系统保留旧任务树，标记需要重新评估的节点及结果，由有权限的人或规划 Buddy 调整计划。

# 状态与执行管理

任务步骤由事实推导，由 flow 模块独占阶段写入。应用用例同事务更新本任务事实和允许的阶段；跨任务影响异步核对。取消、退回和重开为显式受权命令，是否需要验收在创建时固定。见[生命周期](task-flow.md)。

## 建议的业务状态

| 状态 | 含义 | 主要转换条件 |
| --- | --- | --- |
| 待处理 | 信息未齐也可进入的初始状态 | 完成检查及下一状态进入检查通过后推进，未齐保留位置和原因 |
| 执行中 | 正在推进目标 | 等待、提交验收、满足完成规则或取消 |
| 等待（当前状态的附加信息） | 等待输入、决策、依赖、环境或异常处置 | 默认保留当前状态及等待原因；可通过状态接口扩展，但临时阻塞默认保留当前位置 |
| 待验收 | 已有正式交付，等待配置的验收 | 通过后完成；退回后继续或等待 |
| 已完成 | 当前轮及有效依据满足完成规则 | 终态，不可重开；返工新建任务，需求变化不改变已完成任务 |
| 已取消 | 不再推进 | 重新启动必须有明确授权和新记录 |

状态 key 由定义固定，转换与显式控制按核心契约执行。首版确认、异常、不可行用等待/拒绝事实表达，额外状态按需求扩展，不增加隐含流转。可行性结论独立记录为可行、不确定或不可行，并说明依据，不能用“已完成”表达不可行。

任务状态是业务事实；Buddy 在线、消息已读和某次执行成功是不同事实。普通聊天不能直接覆盖正式状态。状态变化记录操作者、原因、时间、依据版本及关联执行。

## 执行记录与所有权

同一任务允许多次执行，分别记录执行 Buddy、具体实例、所依据的目标与计划版本、开始时间、最近进展时间、进度、产物及失效原因。重试、转交或换实例不抹掉旧执行。

首版同一任务同时最多一个有效执行与所有者。并行分工优先通过子任务表达；同节点多执行竞赛作为后续能力。

任务系统维护执行接受、写入隔离和执行者最近进展时间，不设租约或超时、不自动重派；Buddy 负责运行进程、保存可恢复上下文并汇报。自动恢复具体 Agent 内存或任意工具副作用不属于任务系统承诺。

## 中断与取消

- Buddy 断线、休眠、退出或升级后，可重连获取任务、版本、消息与取消事件。

- 掉线和沉默不改变执行事实，也不自动重派；负责人可留言、转交或取消，旧执行写资格随即失效，之后的写入被拒绝。

- 转交或执行失效后，旧结果不能覆盖当前结果；可保留为过期执行的历史产物。

- 重复接受、进度汇报和交付应去重；重试外部动作的幂等性仍需 Buddy 及工具配合。

- 取消立即失效执行写资格；任务系统观察不到外部进程，不声称工具已停止，由 Agent 层在下次读写时得知并自行停止。

- 执行失败可进入重试、等待人工处理或转交，不默认把整个任务永久判定失败。

# 版本与变更管理

## 类似 Git 的使用目标

用户和 Buddy 应能查看当前任务树及状态、追踪历史变更、比较版本、定位结果依据并回看某个时点的工作情况。这里的版本管理不预设采用 Git 存储，也不要求首版具备完整分支合并系统。

## 版本化范围

| 内容 | 记录要求 |
| --- | --- |
| 目标、约束、输入要求和验收标准 | 保留修订版本，展示修改前后差异 |
| 正式计划、任务分解和依赖 | 记录成组变更，能还原历史任务树与关系 |
| 分配、转交和关键角色 | 记录生效范围、原值、新值和原因 |
| 任务状态 | 每次转换有事件历史，可追踪当前状态由何而来 |
| 交付结果 | 每次正式登记有独立版本，引用不可变结果结果 commit及材料版本，关联任务依据和具体执行，不复制正文 |
| 验收流程及结论 | 流程修改与结论分别记录，结论绑定特定交付和验收标准 |
| commit 时间线与进度 | 作为持续时间线记录，追加更正引用可追踪；不要求每条心跳都生成需求修订版 |

## 变更记录与读取能力

每项正式变更记录稳定标识、前序版本、范围、操作者、所代表的身份、时间、原因、修改前后内容及相关任务、执行、交付和决策。跨节点计划变更应能以一次逻辑变更查看。

提供当前版本、变更列表、版本差异、指定时点或版本的树形快照，以及“哪些任务和结果可能过期”的查询。版本号形式、树快照和节点版本如何关联待技术设计。

恢复历史内容应创建新的变更，不删除中间记录。恢复任务信息不会撤销已经发出的邮件、已修改的外部资源等实际副作用。

## 变更影响与结果有效性

目标、约束或验收标准实质变化后，应识别关联执行及下游任务需要重新评估，通知相关 Buddy，并记录继续、调整、重做或停止的决定。系统可以标记潜在影响，是否仍可复用由授权主体判断。

交付须绑定它所满足的目标和验收标准版本。旧版验收通过不得自动证明新版目标完成；目标或结果变化后的重验收规则需要显式确定。

并发修改不得静默覆盖。修改基于过期版本时，应提示冲突或重新评估；具体冲突合并方式待设计。

## 版本能力分期

第一阶段支持必要线性修订及交付证据；任务树在第二阶段，完整树快照、差异及选择性恢复在第三阶段。多方案分支、合并、挑选变更及自动冲突解决列为后续能力，是否必需由实际协作场景决定。

# Buddy 职责与权限模型

## 统一能力与差异授权

不同 Buddy 是独立权限主体。权限不是简单的高低等级，而是“操作能力、作用范围、执行条件”的组合。人和 Buddy 调用相同业务能力，接受相同业务规则和服务端权限检查。

普通执行 Buddy 初期默认没有拆解、转交和修改正式计划的权限；企业可单独向规划、协调、审查或目标维护 Buddy 授权。后续扩大自主程度主要通过配置及开放可调用接口完成，不更换任务流程。

接口对 Buddy 可见与否用于能力发现，服务端授权才是最终约束。即使通过原始 API 调用，也不能越过权限。

## 权限维度

| 维度 | 例子 |
| --- | --- |
| 操作能力 | 阅读、发消息、创建、执行、拆解、分配、修改目标、修改标准、验收 |
| 作用范围 | 指定企业、项目、任务树、单任务、本人负责的任务 |
| 执行条件 | 自主执行、逐次确认、仅可提出建议、禁止 |
| 有效条件 | 授权期限、特定任务、允许的目标参与者、执行与验收分离等规则 |

操作能力和任务可见性需要同时满足。读当前状态、读历史版本和读产物均受相同数据边界约束。“查看所有状态”表示授权范围内可完整查看，不表示全企业或跨企业开放。

## 建议的职责模板

模板仅是可组合的默认集合，不是强制职位，也不代表其中每项能力自动授予。

| 模板 | 主要能力 | 默认不隐含的能力 |
| --- | --- | --- |
| 执行 Buddy | 读取授权上下文、判断可行性、接受执行、汇报、请求输入、提交结果 | 拆解、转交、修改正式计划、目标或验收标准 |
| 规划 Buddy | 创建任务、拆解、调整任务树、维护依赖及正式计划 | 修改上层目标、验收、授权他人 |
| 协调 Buddy | 分配、转交、协调阻塞及任务参与者 | 修改目标与标准、任意扩大参与者可见范围 |
| 审查 Buddy | 阅读交付与依据、提出审查意见；单独授权后验收或退回 | 修改目标、修改标准、代替执行者完成工作 |
| 目标维护 Buddy | 创建或修订目标、约束；另行授权后修改验收标准 | 自动拥有规划、执行、验收或授权管理能力 |

同一个 Buddy 可兼任多个职责。专门审查并调整目标的 Buddy 由“审查＋目标修改”等能力组合表达；审查权限本身不包含改目标。

## 能力分组

- 阅读：任务信息、任务树、commit 时间线、历史版本、差异、执行、结果和验收。

- commit 时间线：发消息、提问、提出建议、回复请求；正式决策另行授权。

- 执行：接受或拒绝、开始、汇报、等待、恢复、交付。

- 规划：创建、拆分、移动、维护依赖、调整正式计划。

- 协调：分配、转交、邀请参与者、请求取消、重试或重开。

- 目标治理：修改目标、约束、验收标准及验收流程。

- 验收：审查意见、通过、退回；审查建议与正式通过分开授权。

- 授权管理：授予与撤销能力，仅授权管理者可执行，不能超出自身可授予范围。

以上是能力语义，不是已定 API 路径。只读、建议、提交待确认变更与直接执行应能清楚区分。

## 授权与身份规则

- Buddy 不直接继承所属用户的全部权限；所属关系用于代理归属和默认路由，具体能力仍需明确授权。

- 凭证绑定逻辑 Buddy，一张凭证即一个运行实例；权限上限由逻辑身份决定。

- 不允许 Buddy 自行扩大权限。若未来允许委派授权，应有单独管理能力和不可突破的上限。

- 需要确认的操作记录确切对象、变更内容和依据版本；确认只授权该项操作，内容变化需重新确认。

- 权限撤销后，后续请求按新权限校验；对进行中执行的停止及工具授权回收需要任务系统与已有管理平台、Agent 层协同，不能承诺抹除已发生副作用。

- 可以配置执行者不得验收自己的结果。人是否也受该规则约束由任务或企业策略确定。

- 所有正式操作记录实际主体、代理归属、授权依据、原因及变更版本。

# 关键业务流程

## 用户自己创建任务

用户创建目标、材料及可选验收标准，默认路由给自己的 Buddy。Buddy 在已有权限范围内判断可行性；明确可行则开始，不足则提出问题，不可行则给出理由和建议。默认路由不授予额外工具权限，也不代表自动获得拆解或修改目标的能力。

执行后提交正式结果，无需独立验收时按完成规则结束，需要验收时进入相应流程。

## 他人交给用户的任务

系统记录任务来源及负责人，用户的 Buddy 先理解并判断是否可以代理接受和处理。不确定意图、职责、资源承诺或权限时，向用户提出确认请求。已被允许自动处理且判断明确的任务可直接推进并保留记录；默认接单授权范围仍需产品策略确定。

## 人规划与多 Buddy 执行

用户拆解根任务、指定依赖和负责人；不同 Buddy 在自己的子任务commit 时间线执行，提交结果并供下游引用。用户调整分解或转交时生成正式变更，相关执行者收到更新。

## 专职 Buddy 规划与协调

获授权的规划 Buddy 可创建和维护子任务及计划，协调 Buddy 可分配和转交。没有相应权限时只能提出建议，不得以发消息替代正式操作。各操作均受任务范围和执行条件限制。

## 审查与目标调整

执行 Buddy 提交指定版本的结果，审查 Buddy 根据对应标准检查并记录结论。只有拥有正式验收权限才能通过或退回；发现目标不合理时，提出修改建议，或在另有目标维护权限时直接修改。修改后重新判断旧结果与验收结论是否适用。

## 目标变更与中断恢复

目标修订形成新版本，系统展示受影响的树节点和执行。授权规划者决定复用、调整、重做或停止。Buddy 断线后按执行所有权和当前版本恢复，过期执行只能补充历史，不能改写当前结果。

## 请求决策

Buddy 在任务内提出具体问题和建议，任务保留当前状态并记录阻塞原因；人或有相应决策权限的 Buddy 回答后，系统关联决策并恢复可执行工作。执行端内部步骤自主选择与正式计划变更分开管理。

# 交付范围与验收场景

## 整体产品范围（分期交付）

| 范围 | 整体目标 |
| --- | --- |
| 任务系统建设 | 独立任务commit 时间线、结构化目标与标准、任务树和依赖、状态、分配、执行记录、结果验收、线性版本历史、差异、权限与审计、业务 API 和持久事件同步 |
| 对接已有管理平台 | 获取 Buddy 身份、有效实例、版本和可用性，处理实例撤销及升级重连对任务的影响；不建设软件分发、实例管理或升级功能 |
| 对接已有 Agent 层 | 提供共用 HTTP 业务 API 和 WebSocket 变化推送，Buddy 按需读取并通过 steer 处理，使用同一 API 提交执行进展和交付；不建设推理、工具执行或执行上下文管理 |

各阶段交付物是对应任务能力及必要的对接。完整任务树、文件和历史恢复不作为第一阶段出口。已有管理平台和 Agent 层自身的功能不作为本项目建设验收项；联调验证其与任务系统的协作行为。

首版权限模型需要支持不同职责与作用范围，不能把所有 Buddy 固定为执行角色。初期默认授权可以保守，特定规划、审查或目标维护 Buddy 按配置获得额外能力。

## 后续候选

公共任务池和能力自动匹配、跨企业协作、复杂会签与多级验收、任务方案分支合并、大规模统计与成本治理、自动任务优先级优化。开放已有能力给特定 Buddy 不应被视为重新建设这些能力。

## 可验证的验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 用户创建任务 | 自己的 Buddy 可按授权判断并开始；目标和标准单独展示 |
| A02 | 他人分配且信息不明确 | Buddy 请求用户确认，待决策项和依据保留 |
| A03 | 普通 Buddy 尝试拆解或转交 | 服务端拒绝，允许其提出建议；经授权后可成功操作 |
| A04 | 规划 Buddy 拆解任务 | 只在授权范围创建树节点和依赖，能查看整次变更 |
| A05 | 多 Buddy 并行执行 | 子任务有独立 commit 时间线和结果，父任务汇总但不提前验收 |
| A06 | 并发修改目标 | 不静默覆盖，后提交者获得冲突或重新评估提示 |
| A07 | 目标从 v1 改为 v2 | 可比较差异及历史任务树，旧结果回复交付标明依据 v1 |
| A08 | 恢复历史计划 | 形成新变更，原历史和既有外部执行事实保留 |
| A09 | 审查 Buddy 没有改目标权限 | 可提意见或按授权验收，修改目标被拒绝 |
| A10 | 配置执行验收分离 | 执行主体无法自行通过；退回关联具体结果版本 |
| A11 | Buddy 掉线后重派 | 新执行有有效所有权，旧执行不能覆盖当前结果 |
| A12 | WebSocket 重复事件和离线重连 | 保留期内按游标补拉；游标过期明确要求重取快照；重复请求不重复改变业务状态 |
| A13 | 执行中取消 | 取消立即失效写资格，不误报工具已停 |
| A14 | 撤销 Buddy 权限 | 后续越权请求被拒绝，记录进行中任务的处置 |
| A15 | 不同企业访问任务与历史 | 当前内容、历史、附件、搜索及引用均无越权泄露 |
| A16 | 已有管理平台升级 Buddy 后重新接入 | 任务系统能识别有效实例并同步当前任务、版本和未处理事件，任务commit 时间线及交付历史不丢失；软件升级功能由已有平台负责 |

补充默认交付验收：一次提交原子创建结果回复与交付引用；普通发言不推进；追加更正 commit 不改变旧交付/验收；文件或链接可单独作为结果；重复提交不重复登记；撤回当前结果不自动恢复旧结果。

以上为需求验收场景，具体测试方法和量化阈值在技术方案阶段确定。

# 非功能需求与待决策事项

## 企业交付与可靠性要求

- 任务系统支持重复部署、配置管理、自身服务升级与数据迁移、任务与附件备份恢复、数据导出和健康观测；Buddy 软件分发和升级复用已有平台。

- 企业边界贯穿查询、历史版本、搜索、事件流和产物访问；不能只在界面隐藏任务。

- 保持任务状态、执行所有权和正式变更的一致性，事件可补拉、重复可识别。

- 完整历史支持分页、过滤、摘要及按版本定位；摘要不能替代原始证据，也不得扩大读取范围。

- 业务日志不包含工具密钥。审计与保留策略需兼顾可追溯和企业数据删除要求。

- 集成接口有稳定版本、鉴权、错误语义及限流；凭证可以撤销。

- 负载与可靠性指标应覆盖在线 Buddy 数、活跃任务数、消息量、事件延迟、恢复时间和历史规模。当前不预设未经确认的吞吐与 SLA 数值。
