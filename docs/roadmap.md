# 路线图：方向与立项门槛

本文给出 Taskloom 的产品定位和候选演进方向，**不是排期**。现有功能已覆盖主要需求（见 [README](../README.md#当前状态)）；下列方向只有在满足各自的立项条件后才进入设计，届时规则仍写进对应的权威文档（[核心契约](core-contracts.md)、[任务流程](task-flow.md)、[API](api.md)），本文只保留方向与链接。

外部参考：德勤《Building the AI-native enterprise》、麦肯锡《The Agentic Organization》、Gartner《The AI-Shaped Organization Reimagines Work, Not Jobs》、BCG《Five Ways That AI Front-Runners Change How Work Gets Done》等关于 AI 原生组织的公开研究。它们提供组织层面的趋势判断，不提供可直接实现的机制，因此只用来校准定位、筛选方向。

## 定位

Taskloom 是**人与 Agent 协作中的行动与问责层**：人负责目标与验收，人或 Agent 处理，每一步都留下可核实的事实。

| 研究中的组织变化 | Taskloom 的对应机制 |
| --- | --- |
| 对业务结果负责，而不只完成任务（BCG） | 人是默认负责人，换处理人不换负责人，见[标识与版本](core-contracts.md#标识与版本) |
| AI 产出，人指导与评价（BCG） | 显式交付与负责人验收结论，见[交付与验收](core-contracts.md#交付与验收) |
| 少数人监督大量 Agent，人管目标、判断和异常（麦肯锡） | Agent 自建与自拆任务，子任务默认免验收，人验收汇总结果，见[任务拆分](core-contracts.md#任务拆分) |
| 从价值出发，反推工作（Gartner） | 目标由父子关系推导，必需子任务放行父任务提交，见[层级与标签](core-contracts.md#层级与标签) |
| 会议从汇报进度转向解决问题（BCG） | 步骤与等待原因由事实推导，问题进入被提问人收件箱，见[推导什么](task-flow.md#推导什么) |

德勤把 AI 原生企业的"认知层"分为 Knowing、Acting、Learning。Taskloom 只承担其中 **Acting 的事实记录**，并为 Learning 提供原始事实；共享业务情境、上下文组装、记忆属于 Agent 层（AgentKit、NEX），不在本项目范围内。

## 立项门槛

新方向进入设计前，须同时满足：

1. **有真实读取方**：能指出谁、在什么场景下读取它并据此做决定；"以后可能有用"不算。
2. **由已有事实推导**：优先做只读的推导视图；需要新增存储时，先说明为什么无法从现有事实推导。
3. **不越界**：不建设模型推理、工具执行、上下文组装、远端派发、确认工作流和后台扫描。
4. **公共契约变更先确认**：涉及 `cap/*`、API、MCP 工具或行为契约时，按 [AGENTS.md](../AGENTS.md#插件与接口) 先说明必要性、通用性、兼容性和受影响消费者。

## 候选方向

### R1 需要介入的任务视图

- **问题**：一个人监督的 Agent 数量变多后，逐条看任务看不过来，需要只把要人介入的任务挑出来。
- **最小形态**：在任务列表上加只读过滤，返回负责人名下符合任一条件的任务：长时间没有进展（阈值由请求参数给出，读取时计算）、等待验收、有未回答问题、结果依据已失效、必需子任务已取消导致父任务无法提交。每行带原因。
- **已有基础**：`GET /tasks?mine=true` 已覆盖"轮到我处理"和"等待必需子任务"（见 [API](api.md#空间项目与任务)）；执行已记录最近进展时间，但列表行尚未返回它。
- **约束**：不新增状态，不做后台扫描，不自动提醒或改派；沉默不改变执行，见[执行与写入隔离](core-contracts.md#执行与写入隔离)。
- **立项条件**：有负责人实际同时管理足够多的 Agent 任务，且现有"我的工作"不够用。
- **待定**：阈值是否需要部署默认值；是否同时提供 MCP 工具（读取方是代表负责人巡检的 Agent 时才需要）。

### R2 验收方式的选择指引

- **问题**：BCG 观察到领先企业按风险和可逆性分配决策权。Taskloom 已有对应机制：验收方式 `manual`/`none` 在创建时固定，Agent 可分配范围由部署配置限定。缺的是何时用哪种的指引。
- **最小形态**：一份使用指引，例如"产生外部副作用或难以撤回的结果用 `manual`；可在后续任务中返工的内部工作用 `none`"；可配合推荐标签标示风险类别（标签只用于分类筛选，不影响流程）。
- **约束**：不新增审批流或按风险自动选择验收方式；工具调用层面的审批归 AgentHub。
- **立项条件**：在真实使用中出现验收方式选错（过多无意义的人工验收，或该验收的没有验收）。

### R3 结果质量报告

- **问题**：德勤强调组织要从执行结果中学习；BCG 指出评价应看判断质量而非工作量。Taskloom 已有原始事实：验收结论与退回理由、重新提交、更正记录。
- **最小形态**：按处理人（人或 Agent）、项目、标签和时间段，推导交付次数、首次通过率、退回次数与理由列表、从认领到完成的耗时。只读，读取时计算。
- **约束**：不存分数或排名，不用于人的绩效打分；按现有任务读权限过滤，只汇总调用者可读的任务。
- **待定**：Taskloom 不记录 Agent 执行时用了哪些 skill，客户端自述不可核实（见[执行与写入隔离](core-contracts.md#执行与写入隔离)），因此不按 skill 归因，除非出现可核实的来源。
- **立项条件**：有人要据此决定"哪类任务交给 Agent""哪个 Agent 需要调整"。

### R4 决策摘要

- **问题**：BCG 案例中，会议前由 Agent 整理已做出的决定和待解决的问题。Taskloom 的 commit 时间线里已经有这些事实。
- **最小形态**：给定项目或目标子树和时间段，列出期间的验收结论、问题与回答、依据修改、负责人移交、取消与重开，以及当前未回答的问题。只读，引用原 commit，不复制正文。
- **约束**：只汇总明确的命名命令产生的事实，不从留言自然语言里猜测决定（见[架构](architecture.md#只存能核实的事实)）；不生成文字总结，总结归 Agent 层。
- **立项条件**：有固定的评审或周会场景在用它替代人工整理。

### R5 Skill 控制面的业务价值

- **问题**：Workera 案例把专家知识整理成 Agent 可调用的资料。这正是 [Skill 交付控制面](skills.md) 的作用，目前缺少把它和任务结果联系起来的叙事。
- **方向**：先作为定位与对外说明；功能上的联系（如把退回理由反馈给 skill 维护者）依赖 R3 和可核实的 skill 归因，暂不展开。

## 明确不做

- **认知层的上下文与记忆**：共享业务情境、上下文组装、长期记忆属于 Agent 层。
- **OKR 量化指标与进度百分比**：目标进度已由子树事实汇总；没有读取方的指标字段不预建。
- **人的绩效评分**：R3 只给事实统计，不打分、不排名。
- **自动催办、超时改派与审批工作流**：与[执行与写入隔离](core-contracts.md#执行与写入隔离)和"不建设确认工作流"（见[命令、权限与事务](core-contracts.md#命令权限与事务)）冲突。
